Scan date: 2026-10-18. musubi revision: `main` of https://github.com/musubi-oss/musubi cloned the same day. Competitor revisions: agones `main` (CHANGELOG head v1.61.0), open-match `master` (v1.8.1), open-match2 `main` (v2.0.2), open-match-docs `master`.

## Top gaps for musubi

Ranked by how much a studio choosing between "Agones + Open Match" and musubi would care.

1. **Dedicated-server SDK libraries (Unreal DS, Unity, C++, C#, Go, Rust, Node, Python) with a `WatchGameServer` push stream.** Sketch: publish `musubi-gameserver-sdk` (Rust crate) over the existing HTTP routes, generate C/C++/C# bindings from it, add a WebSocket or SSE variant of `GET /v1/gameserver/watch`, ship an Unreal DS plugin and a Unity package; keep the REST path as the conformance reference.
2. **Pluggable external match function (Open Match's whole value proposition).** Sketch: add a `MatchFunction` provider per queue — `wasm` (module ABI gets `tickets`, returns `matches`) and `http`/`grpc` (`POST /run {queue, tickets[]}` → matches) — invoked by the leader pass with timeout + fallback to the built-in algorithm; expose `GET /v1/server/matchmaker/queues/{name}/tickets` so external code can query pools.
3. **Label/attribute selectors on allocation.** Sketch: extend `POST /v1/server/allocate` with `selectors[{labels, expressions, state}]` evaluated in order over `game_servers.labels` (GIN index), returning the first match; this also unlocks Agones' label-locking and two-fleets patterns.
4. **Generic counters and lists per server.** Sketch: `game_servers.counters jsonb` / `lists jsonb` with declared keys + capacities in `FleetSpec`, SDK `POST /v1/gameserver/counters/{key}` (`set/inc/dec/capacity`) and `…/lists/{key}` (`add/remove/capacity`), allocation filters `counters{key:{minAvailable,…}}` and actions, autoscaler target "free capacity of key".
5. **Autoscaling policies beyond buffer/schedule: percentage buffer, webhook, WASM, cron+timezone schedule, chain with fallback.** Sketch: `ScalePolicy` becomes an enum list evaluated in order (`buffer{abs|pct}`, `capacity{key}`, `schedule{cron, tz, duration, policy}`, `webhook{url, ca}`, `wasm{module}`), each returning `Option<desired>`; keep the EWMA forecast as another policy.
6. **Reserved state and rolling updates for Ready servers.** Sketch: add `reserved_until` + `POST /v1/gameserver/reserve {secs}` (excluded from allocation and scale-down); on build promote, drain `ready` servers of the old version at `max_unavailable` per pass and replace them with the new build (`strategy: rolling|recreate|new-only`).
7. **Configurable health policy and disruption semantics.** Sketch: `FleetSpec.health{initial_delay_secs, period_secs, failure_threshold, disabled}`; an explicit `unhealthy` state with a restart-vs-replace rule; for the k8s/agones providers emit `safe-to-evict`/PDB from a `disruption: never|on_upgrade|always` field.
8. **Multiple ports and protocols per server.** Sketch: `ports[{name, protocol udp|tcp|both, policy dynamic|static|none}]` in `FleetSpec`, `MUSUBI_PORT_<NAME>` env, `ports[]` in the allocation response.
9. **Allocation ranking (priorities) and placement strategy.** Sketch: `priorities[{field|counter, order}]` + `scheduling: packed|distributed` on the request; implement as `ORDER BY` on the candidate query plus per-node occupancy from `node_id`.
10. **Autoscaler/allocation observability parity.** Sketch: export `musubi_fleet_desired_servers`, `musubi_fleet_autoscaler_limited`, `musubi_gameserver_allocation_duration_seconds`, `musubi_gameserver_state_duration_seconds` (from `ready_at`/`terminated_at`), `musubi_fleet_allocations_total{fleet}`; ship Grafana dashboards + a ServiceMonitor in the Helm chart.
11. **Multi-cluster / multi-control-plane allocation.** Sketch: `GET/POST /v1/server/allocate` accepts `clusters[{endpoint, key, priority, weight}]` and the node proxies to remote musubi clusters with timeout + fallback, mirroring `GameServerAllocationPolicy`.
12. **Richer Pod/VM template for the k8s, agones and firecracker providers.** Sketch: allow `resources{cpu,memory}`, `node_selector`, `tolerations`, `image_pull_secret`, `sidecars[]`, `termination_grace_secs` in `FleetSpec`, passed through to the Pod/CR; Windows image support for the k8s provider.
13. **Feature flags / stability tiers and upgrade runbook.** Sketch: `[features]` table with alpha/beta/stable gates documented per release, plus an "upgrade without dropping matches" document (drain node → migrate → rolling restart) and a changelog that marks breaking changes.
14. **Typed API clients and a declarative resource model.** Sketch: generate Go/TypeScript/C# clients from `openapi.json` in CI; make `musubi deploy` idempotent for every resource (fleets, queues, schemas, modules) so a repo of TOML is the equivalent of `kubectl apply`.
15. **Examples and tutorials for the dedicated-server path.** Sketch: `examples/` with a Go/Rust/C++ `simple-game-server` that uses the HTTP SDK, an Unreal DS sample, an "Agones provider on GKE" walkthrough and a Matchmaker-101-style tutorial (queue → ticket → allocation → connect token).

### Open Match (OM1 1.4 2022-08 → 1.8.1 2023-12; OM2 preview 2025–2026)

- OM1 releases 1.4–1.8 were maintenance: Redis chart/version bumps, HPA per service (1.6), configurable override from values (1.6), `persistent_field` on tickets (1.5), ticket-behaviour metrics and dashboards (1.5), Redis Enterprise tutorial and Go 1.19 (1.7), security dependency bumps (1.8.x). The repo's last commit is a 2024-07 dependency bump.
- OM2 (separate repo `open-match2`) is a re-architecture: one `om-core` binary, REST via grpc-gateway as the recommended client path, Redis read/write split with an in-memory ticket cache, env-var configuration, Buildpacks images, removal of Synchronizer/Evaluator (the matchmaker now owns collision resolution), tickets inactive at creation with mandatory TTL, bidirectional `InvokeMatchmakingFunctions` stream that pushes tickets to MMFs in chunks, assignment delivery moved to the matchmaker, Cloud Run/GKE deployment manifests, OpenTelemetry sidecar. Docs updated through 2026-03 (gcloud storage migration) and 2026-01 (JP FAQ on TTL).
- Direction of travel: Google is narrowing Open Match to a thin ticket cache + MMF invoker tuned for Google Cloud; OM1 is effectively frozen. A studio adopting Open Match today is adopting a preview with a small ecosystem (`open-match-ecosystem`, Space Agon).
